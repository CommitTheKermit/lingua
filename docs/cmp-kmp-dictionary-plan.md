# CMP/KMP 영한 사전 목표 구조와 구현 계획

## 문서 목적

이 문서는 Flutter 구현의 단계별 마이그레이션 절차가 아니라, Android와 iOS를 대상으로 한
Compose Multiplatform 및 Kotlin Multiplatform 포팅이 완료된 시점의 영한 사전 목표 구조와
구현 순서를 정의한다.

## 목표 상태

- Android와 iOS가 동일한 Compose Multiplatform 사전 UI와 화면 상태를 사용한다.
- 기본 조회는 위키낱말사전 기반 SQLite 번들로 완전히 오프라인 동작한다.
- 사전에 없는 단어만 사용자가 직접 요청할 때 기존 `translateProxy`로 번역한다.
- DeepL 키는 앱에 포함하거나 앱으로 전달하지 않는다.
- Glosbe, WiktApi 등 외부 사전 API에 런타임 의존하지 않는다.
- 데이터 출처와 CC BY-SA 4.0 라이선스를 앱에서 확인할 수 있다.

```text
Compose Multiplatform UI
        |
DictionaryViewModel
        |
DictionaryRepository
   |                |
로컬 SQLite      translateProxy
   |                |
위키낱말사전 DB    DeepL
```

## 데이터 생성 파이프라인

기존 Python 생성 방식을 Kotlin으로 다시 만들지 않고 앱 외부의 빌드 도구로 유지한다.

1. Kaikki가 Wiktextract로 구조화한 한국어 위키낱말사전 추출물을 입력으로 사용한다.
2. 한국어판에 직접 작성된 영어 표제어만 추출한다.
3. 한국어 표제어의 영어 번역을 역색인한 데이터는 제외한다.
4. 표제어의 대소문자와 공백을 정규화하고 빈 뜻과 중복 뜻을 제거한다.
5. 활용형을 별도 조회 키로 만들어 원래 표제어와 연결한다.
6. 결과를 SQLite 파일과 라이선스 `NOTICE` 파일로 생성한다.
7. 입력 URL, 생성일, 데이터 버전, 라이선스와 체크섬을 메타데이터에 기록한다.
8. 생성된 DB를 저장소에 포함해 일반 앱 빌드가 네트워크에 의존하지 않게 한다.

사전 자동 갱신 서비스는 만들지 않는다. 출시 준비 시 생성 명령을 수동 실행하고 품질 검증을
통과한 데이터만 갱신한다.

## 최소 데이터 모델

```text
dictionary_entry
- id
- headword
- part_of_speech

dictionary_sense
- entry_id
- sequence
- korean_definition

dictionary_lookup_key
- lookup_key
- entry_id
- priority

dictionary_metadata
- data_version
- source_url
- license
- generated_at
```

정확 일치와 사전에 미리 생성한 활용형 키 조회만 제공한다. FTS, 오타 교정, 발음, 어원,
유의어와 예문은 초기 범위에서 제외하고 실제 읽기 경험에서 필요성이 확인될 때 추가한다.

## KMP 데이터 계층

### `commonMain`

- `DictionaryEntry`와 `DictionarySense`
- 검색어 정규화
- SQLite 조회와 결과 정렬을 담당하는 `DictionaryRepository`
- `DictionaryUiState`
- `StateFlow`를 노출하는 `DictionaryViewModel`
- 품사별 결과 그룹화

사전 구현 하나를 위해 인터페이스와 구현체를 따로 만들지 않는다. 테스트는 SQLite 테스트 DB와
번역 호출 함수 주입으로 해결한다.

### 플랫폼 코드

플랫폼별 코드는 다음 두 부분으로 제한한다.

- Android와 iOS용 SQLite 드라이버 생성
- 앱 번들에 포함된 DB를 최초 실행 시 읽기 전용 저장소로 설치

프로젝트가 SQLDelight를 사용하면 같은 스택을 재사용한다. 사전 하나 때문에 별도 ORM이나 검색
라이브러리를 추가하지 않는다.

사전 DB는 사용자 데이터와 분리한다. 앱에 더 새로운 데이터 버전이 포함되면 임시 파일에 설치한
후 기존 파일을 원자적으로 교체해 업데이트 중 손상 가능성을 막는다.

압축은 출시 빌드 크기를 측정한 뒤 결정한다. 압축이 다운로드 크기를 실질적으로 줄이지 않으면
플랫폼별 압축 해제 코드 없이 SQLite 파일을 그대로 번들한다.

## 조회 흐름

1. 사용자가 본문 단어를 누르거나 사전 검색창에 입력한다.
2. 공백과 구두점을 제거하고 조회 키를 정규화한다.
3. `dictionary_lookup_key`에서 정확 일치 항목을 찾는다.
4. 결과를 품사와 의미 순서대로 반환한다.
5. 결과가 없더라도 자동으로 네트워크를 호출하지 않는다.
6. 사용자가 `DeepL로 번역`을 누른 경우에만 `translateProxy`를 호출한다.
7. 네트워크 실패와 번역 쿼터 부족을 로컬 사전의 결과 없음 상태와 구분한다.
8. 조회 기록이 필요하면 결과 표시 성공 후 별도로 저장하며 기록 실패가 조회를 막지 않게 한다.

## CMP UI 계획

### 해결할 문제

- 오프라인 사전 결과와 온라인 번역 결과를 사용자가 혼동하지 않게 한다.
- 사전 누락만으로 번역 쿼터가 자동 소모되지 않게 한다.
- 본문 선택 조회와 직접 입력 조회가 같은 결과 화면을 사용하게 한다.

### 구현할 UI

하나의 공용 적응형 사전 모달을 사용한다.

- 상단에 조회한 영어 단어를 표시한다.
- 본문에 품사별 한국어 뜻 목록을 표시한다.
- 결과가 없으면 `사전에 없는 단어입니다` 상태를 표시한다.
- 결과 없음 상태에서만 `DeepL로 번역` 동작을 제공한다.
- 온라인 결과에는 `번역 결과`임을 명확히 표시한다.
- 하단에 위키낱말사전 출처를 표시한다.
- 읽기 화면 메뉴의 `사전 검색`에서 직접 입력할 수 있다.
- 본문 단어를 선택하면 같은 모달을 검색어가 입력된 상태로 연다.

Android와 iOS에 별도 화면을 만들지 않는다. 화면 크기에 따라 모달의 크기와 배치만 조정한다.

## 온라인 번역 보완

- 앱은 Firebase `translateProxy`만 호출한다.
- DeepL 키 조회 API와 클라이언트 직접 호출은 제거한다.
- 인증, App Check와 쿼터 검증은 서버에서 처리한다.
- 번역 결과는 위키낱말사전 데이터와 섞어 저장하지 않는다.
- 캐시는 프로젝트의 기존 번역 기록 저장소가 있으면 재사용한다.

## 현재 Flutter 구조에서 가져가지 않을 부분

이 절에서 인용하는 `lingua_flutter/...` 경로는 Flutter 원본 기준이다. Flutter 코드는
`legacy/flutter` 브랜치에 보존되어 있고 그 브랜치에서는 루트 레이아웃이므로,
`lingua_flutter/lib/...` 경로는 `lib/...`로 읽는다.

### `ApiUtil`의 책임 집중

`lingua_flutter/lib/util/api/api_util.dart`는 사전 조회, 단어 기록, 사용자 요청, DeepL 호출과
비밀값 취득을 한 클래스에서 처리한다. 단일 책임 원칙을 위반하고 구체적인 HTTP 및 전역 상태에
의존해 의존성 역전 원칙도 위반한다. CMP/KMP 구현에서는 이 구조를 복제하지 않는다.

### UI 렌더링 중 데이터 변경

`lingua_flutter/lib/widgets/read_widgets/dictionary_result_widget.dart`는 `build` 중에 중복 결과를
병합하고 전달받은 목록과 모델을 직접 변경한다. 표시와 데이터 가공 책임이 섞인 단일 책임 원칙
위반이며, 렌더링 재실행에 따라 결과가 달라질 수 있다. 데이터 정리는 저장소에서 한 번 수행하고
UI는 불변 화면 상태만 그린다.

### 읽기 화면의 책임 집중

`lingua_flutter/lib/screens_mobile/main_screens/read_screen.dart`는 페이지 이동, 파일 저장, 번역,
쿼터와 UI 상태를 함께 처리한다. 단일 책임 원칙을 위반하므로 사전 기능을 이 화면 상태에 추가하지
않고 별도 `DictionaryViewModel`에 둔다.

## 구현 순서

1. 실제 영어 원서에서 대표 단어 표본과 기대 결과를 확정한다.
2. 위키낱말사전 SQLite 생성기와 라이선스 산출물을 완성한다.
3. KMP SQLite 드라이버와 읽기 전용 DB 설치를 연결한다.
4. `DictionaryRepository`와 공통 조회 테스트를 작성한다.
5. `DictionaryViewModel`과 불변 화면 상태를 작성한다.
6. CMP 사전 모달과 직접 검색 진입점을 연결한다.
7. 사용자 선택형 `translateProxy` 보완을 연결한다.
8. 라이선스 고지와 Android 및 iOS 출시 빌드를 검증한다.

## 검증 계획

### 데이터 생성기

- 같은 입력으로 같은 DB가 생성되는지 확인한다.
- 빈 뜻과 중복 뜻이 제거되는지 확인한다.
- 한국어 표제어의 영어 번역 역색인 데이터가 섞이지 않는지 확인한다.
- 활용형이 올바른 표제어를 가리키는지 확인한다.
- 라이선스, 출처와 데이터 버전이 산출물에 포함되는지 확인한다.

### 공통 코드

- `dog`, `run`, `bank`처럼 기본 뜻과 다의어가 있는 단어를 조회한다.
- 불규칙 활용형을 원래 표제어로 조회한다.
- 대소문자, 공백과 구두점을 정규화한다.
- 없는 단어는 빈 결과를 반환한다.
- 품사와 의미 순서를 유지한다.
- 새 데이터 버전 설치 후 새 DB를 조회한다.

### UI 상태

- 검색 전
- 로컬 검색 결과
- 결과 없음
- 원격 번역 진행 중
- 원격 번역 성공
- 네트워크 오류
- 번역 쿼터 부족

### 플랫폼 검증

- Android와 iOS에서 같은 단어가 같은 결과를 반환한다.
- 비행기 모드에서 기본 사전 조회가 성공한다.
- 최초 DB 설치와 앱 업데이트 후 DB 교체가 성공한다.
- 앱 패키지에 DB와 라이선스 고지가 포함된다.
- 앱 바이너리와 로그에 DeepL 키가 없다.

## 완료 조건

- 기본 사전 조회가 네트워크 없이 동작한다.
- Android와 iOS의 검색 결과가 동일하다.
- 미검색 단어에서만 사용자가 DeepL 호출을 선택할 수 있다.
- API 키가 클라이언트에 존재하지 않는다.
- 데이터 생성 과정이 재현 가능하다.
- 라이선스와 출처가 앱 및 배포물에 포함된다.
- 대표 원서 단어 표본에서 기존 역색인 DB보다 정확한 결과를 제공한다.

## 의도적으로 제외한 항목

- 별도 사전 서버
- 외부 사전 API 런타임 의존
- 검색 엔진과 오타 교정
- 자동 데이터 업데이트
- 발음, 어원, 유의어와 예문

제외한 항목은 실제 사용자 요구나 측정된 품질 문제가 확인될 때만 추가한다.
